# 团队版 Bongcat 活动面板 — 实施计划

> 把现有「个人 AI 额度监视器」扩展出一个**团队版活动面板**：同一局域网的 2~3 人互相看到彼此的 AI 是否在干活，用拍桌猫（Bongo Cat）动画可视化。开发工具版的 Rich Presence。
>
> 本文重点章节：**第 4 节「网络与部署方案」**（按部署负担从轻到重铺开，含决策树）。

---

## 1. 目标与边界

- **要做**：局域网内的「谁的 AI 正在跑」状态广播 + 猫动画面板。
- **不做（v1）**：上云、跨公网、进程 hook、精确任务描述。
- **环境前提**：成员都在国内、同一办公网 / 局域网 → **不碰境外服务，优先零服务器**。
- **形态决策（已定）**：现有额度监视器**保持不动**；团队面板做成**独立的第二个 exe**，两个程序互不影响，只共用「读本地 token」的逻辑。
- **活动信息粒度（已定）**：显示 **工具 + 项目名**（如 `claude code · LLMMonitor`），项目名从会话日志路径提取。完整任务描述留 v2。

---

## 2. 整体架构（三层）

```
[本地活动检测]  →  [局域网状态同步]  →  [面板里画猫]
   复用 usage.rs        UDP / WS          独立 exe 前端
   token 增量→busy      见第 4 节         bongcat-panel
```

- **本地活动检测**：复用现有 `usage.rs` 的 token 扫描，比较两次采样增量。涨了=busy，连续不涨=idle。
- **状态同步**：把本机状态广播出去 + 收别人状态。**本节是部署关注点，见第 4 节**。
- **可视化**：每个成员一只猫，busy 拍手、idle 打盹。UI 基于已有原型 `docs/files/bongcat-panel.html`。

---

## 3. 复用 vs 新增

| 模块 | 来源 | 说明 |
|---|---|---|
| 读本地 token | **复用** `usage.rs::scan_claude_today/scan_codex_today` | 活动检测的数据源，零额外成本 |
| 活动检测 | 新增（小逻辑） | token 增量 → busy 布尔；提取项目名 |
| 身份/配置 | 新增 `config.rs` | 我的显示名、端口、（WS 模式下）主机 IP |
| 网络同步 | 新增 `presence.rs` | 广播/监听 + peer 表 + 离线判断 |
| 面板 UI | 改造原型 | 独立 exe 前端，接收 peer 事件画猫 |

> 独立 exe 实现方式：新建一个并列的小 Tauri 工程（或 cargo workspace 成员），把 `usage.rs` 抽成共享逻辑两个 app 都用。

---

## 4. 网络与部署方案 ⭐（重点）

核心结论先说：**首选 UDP 方案，根本不需要任何服务器，零部署**。只有当办公网屏蔽广播时，才退到需要「一个常驻进程」的 WebSocket 方案。下面按**部署负担从轻到重**给三个档位。

### 方案 A：UDP 局域网广播 —— 零服务器、零部署 ✅ 首选

每台机器既往局域网广播自己的状态，又监听别人的。**没有中心节点、没有服务器进程、没有 IP 配置**，谁开机谁加入，谁关机谁消失。

```
A机 ⇄ 广播(255.255.255.255:48888) ⇄ B机
         ⇅
        C机
```

- **部署成本**：**零**。装上 exe 打开就行，不需要任何人维护任何服务。
- **单点故障**：无。任何一台关机不影响其他人。
- **配置**：只需所有人端口一致（默认 48888）。名字各自填。
- **唯一要求**：网络允许 UDP 广播、且大家在同一网段。
- **现状**：单机自测已通过（你的机器 `10.1.73.47`，广播收发 ✅）。**还差两台机器实测**——脚本已备好 `tools/udp-lan-test.js`，两人各跑一次看能否互相发现。
- **唯一“部署动作”**：首次运行 exe 时 **Windows 防火墙会弹窗**，点「允许」即可（一次性）。

> **如果双机测试通过，部署这件事到此结束——没有服务器要管。** 这是最省心的形态。

### 方案 B：应用内置「主机模式」WebSocket —— 无独立服务器 ⚖️ 备选

如果 UDP 不通（企业网禁广播 / 客户端隔离），退到 WebSocket，但**不单独部署服务器**：把一个极简 WS 服务**内置进面板 exe**，谁愿意当主机就在设置里打勾「我是主机」，其余人填**主机的内网 IP**。

```
       B(客户端) ─┐
                  ├─→ A(主机模式，内置WS) ──→ 广播给所有人
       C(客户端) ─┘
```

- **部署成本**：**很低**。不用装第二个程序，主机就是某人的面板 app 本身，勾一个选项。
- **配置**：客户端要填主机 IP（如 `ws://10.1.73.47:48889`）。可做成「设置里填一次」。
- **单点**：主机关机 → 状态中断（其他人面板标灰）。重开或换人当主机即可。
- **适用**：UDP 不通、但大家能互相访问对方 IP（同网段、无端口隔离）。

### 方案 C：独立 WebSocket 服务（常驻） 🛠️ 最稳但要维护

如果连「让某人开着面板当主机」都不稳定（比如主机的人经常关机），就把那十几行 WS 服务做成**一个独立小程序，挂在一台常开机器上常驻**（某人的台式机 / 一台 NAS / 一个小盒子）。

**怎么常驻（Windows）**：
- 简单：终端里 `node server.js`，但关终端就停。
- 推荐：用 **nssm** 或 **PM2** 把它注册成 **Windows 服务 / 守护进程**，开机自启、崩溃自拉。
  - 例：`nssm install LLMMonitorRelay "C:\path\node.exe" "C:\path\server.js"`
- **防火墙**：在那台机器放行 WS 端口（如 48889）。
- 客户端都填这台机器的内网 IP。

- **部署成本**：**最高**（要选一台机器、装运行时、注册服务、放行端口、维护它别挂）。
- **回报**：最稳，主机不依赖某个人开不开电脑。
- **适用**：团队稍大、要长期稳定运行。

### 三档对比

| | A. UDP 广播 | B. 内置主机模式 WS | C. 独立 WS 服务 |
|---|---|---|---|
| 要不要服务器 | **不要** | 不要（某人当主机） | 要（一个常驻进程） |
| 部署动作 | 装 exe + 防火墙放行 | 勾「主机」+ 填 IP | 选机器+装服务+放行+维护 |
| 单点故障 | 无 | 主机关机即断 | 服务挂即断 |
| 要填 IP 吗 | 否 | 要（填主机 IP） | 要（填服务 IP） |
| 运维负担 | 零 | 极低 | 中 |
| 推荐度 | ⭐⭐⭐ 首选 | ⭐⭐ UDP 不通时 | ⭐ 要长期稳定时 |

### 决策树

```
两台机器跑 udp-lan-test.js
        │
   互相看到？
   ├─ 是 → 方案 A（UDP），到此无需服务器 ✅
   └─ 否 → 能互相 ping 通对方 IP？
            ├─ 是 → 方案 B（内置主机模式 WS）
            └─ 否（强隔离）→ 方案 C（独立 WS 服务挂常开机）
```

> **我的建议**：先按方案 A 实现（绝大多数办公网 UDP 广播是通的），并把网络层**抽象成一个 `Transport` 接口**——这样万一以后要切 B/C，只换传输实现，活动检测和 UI 都不用动。

## 5. 活动检测设计

- 复用 `usage.rs` 已有扫描，得到「当前累计 token」。
- 在面板 app 里以较快节奏（如每 8~10s）采样一次：
  - `delta = 本次累计 − 上次累计`
  - `delta > 阈值` → busy；连续 `N` 次（约 60~90s）无增长 → idle（防止两轮对话间的短暂停顿误判）。
- **项目名提取**：取最近改动的会话日志路径，解码出工程名。
  - Claude：`~/.claude/projects/D--CursorProject-LLMMonitor/...` → `LLMMonitor`
  - Codex：从最近 `sessions/.../rollout-*.jsonl` 的 `cwd` 字段取。
- **工具判断**：Claude 还是 Codex 哪个的 token 在涨，就报哪个在跑。

---

## 6. 状态协议（每条广播/推送消息）

```json
{
  "instance": "机器唯一ID",      // 过滤自己 + 区分 peer
  "name": "班定悦",              // 可配置显示名
  "busy": true,
  "tool": "claude",              // claude | codex | null
  "project": "LLMMonitor",       // 当前工程名
  "tokensToday": 468000000,      // 今日 token，面板格式化成 万/亿
  "ts": 1780000000               // 发送时间，用于离线判断
}
```

- 广播频率：~3s 一次。
- **离线判断**：每个 peer 记 `last_seen`，超过 ~15s 无消息 → 标灰；更久 → 移除。

---

## 7. UI（独立 exe）

- 基于 `docs/files/bongcat-panel.html`：每个成员一张卡（猫 + 名字 + 工具·项目 + token），`busy` 拍手冒音符、`idle` 打盹冒 z，全 CSS 无图片依赖。
- 接 `presence.rs` emit 的 peer 事件，维护 peer 列表渲染。
- 窗口：独立置顶小窗（比额度窗宽一点，~340px），可拖动、托盘管理，和额度 exe 各自独立。

## 8. 分阶段实施

| 阶段 | 内容 | 依赖 | 产出 |
|---|---|---|---|
| **0. 验网络** | 双机 `udp-lan-test.js` | 一个同事 | 决定 A / B / C |
| 1. 脚手架 | 新建独立面板 Tauri 工程，抽出共享 `usage` 逻辑 | — | 空面板能跑 |
| 2. 活动检测 | token 增量→busy + 项目名/工具 | usage 复用 | 本机能判断自己 busy |
| 3. 配置 | `config.rs`：名字/端口/(主机IP) | — | 可填自己名字 |
| 4. 传输层 | `presence.rs`：`Transport` 抽象 + UDP 实现（A） | 阶段 0 通过 | 两机能互发 |
| 5. 面板 UI | 接 peer 事件画猫 + 离线标灰 | 2/4 | 完整团队面板 |
| 6. 打包 | 第二个安装包（面板 exe） | 全部 | 可分发 |
| (后续) | B/C 传输实现、完整任务描述、历史回放 | — | v2 |

## 9. 风险与坑

- **UDP 被屏蔽 / 客户端隔离**：必须先做阶段 0。不通就切 B/C。
- **跨网段**：`10.1.73.x` 和 `10.1.74.x` 之间 `255.255.255.255` 一般不通；同段才稳，否则用 WS。
- **Windows 防火墙**：首次运行 exe 会弹窗，要放行（每台机器一次）。
- **隐私**：广播会让同网段所有人看到你「在忙 + 工具 + 项目名 + token」。项目名是否广播可做成开关。
- **离线检测必须做**，否则关程序的人一直挂在面板上。
- **别过度设计**：v1 活动检测就用最简单的 token 增量，不 hook 进程。

---

## 10. 待你拍板的点

1. **网络方案**：等双机测试结果。通 → A；不通 → B 还是 C（取决于你们愿不愿意维护一个常驻服务）。
2. **项目名广播**：要不要默认广播项目名（涉及隐私），还是做成开关 / 只显示工具不显示项目。
3. **是否并行**：阶段 1、2、5（不依赖网络的：脚手架 + 活动检测 + 面板 UI）可以现在就先做，等网络结论出来再接传输层。要不要先并行推进？
